# 新增功能的思考过程

本文记录「为 MiniDB 新增一个 SQL 功能」时我实际采用的分析方法,以这次「支持 EXISTS → 标量子查询 → IS NOT DISTINCT FROM」的推进过程为实例。重点不是结论本身(结论见 `原理.md`),而是**每一步为什么这么做、什么时候停下来验证、什么信号说明之前的假设错了**。

## 核心方法:探清现状,不凭假设动手

新增功能的第一反应很容易是「我知道 Calcite 怎么处理 EXISTS,直接写代码」。但 Calcite 版本、`SqlToRelConverter` 配置、已有规则集都会让同一段 SQL 转成完全不同的 RelNode。所以第一步永远是**用一次性探针把真实计划打印出来**,而不是凭印象。

具体做法:写一个 `@Test` 探针,构造 `Planner`,对目标 SQL 调 `planner().plan(sql)`,再 `RelOptUtil.toString(rel)` 打印。例如:

```
SELECT * FROM a WHERE EXISTS (SELECT 1 FROM b WHERE b.aid = a.id)
```
打印出:
```
MiniDbFilter(condition=[EXISTS({ LogicalFilter(=($1, $cor0.id)) LogicalTableScan(b) })])
```

这一步立刻纠正了一个关键认知:**EXISTS 并没有被转成 SEMI join,而是作为 `RexSubQuery` 内嵌在 Filter 条件里**,相关列用 `$cor0.id` 引用。根因不是「缺 SEMI join 算子」,而是「`RexInterpreter` 没有 `RexSubQuery` 求值分支」。

> 教训:动手前先打印真实 RelNode。假设「Calcite 会把 EXISTS 变成 join」在 `expand=false` 的默认配置下是错的。

## 选路径:优先复用成熟管线,不自己造算子

确认现状后,有两种改法:

1. 自己写 `RexSubQuery` 求值 + 相关变量绑定(执行期去相关)——侵入 `RexInterpreter`,要处理 `$cor0` 相关变量,复杂度高。
2. 用 Calcite 标准管线:`SubQueryRemoveRule`(RexSubQuery → LogicalCorrelate)→ `RelDecorrelator`(Correlate → 普通 join/聚合)。

我选了 2,并用探针验证了去相关产物**只含已有算子**(join/聚合/过滤/投影),无需新物理算子、无需 SEMI/ANTI。这是「让成熟组件替我解决难题」的典型取舍:自己实现等于重造 `RelDecorrelator`。

## 让测试暴露隐藏问题

接入去相关后,跑测试发现**非相关 EXISTS 在子查询为空时崩溃**,相关 EXISTS 却正常。追根是三个 join 子类用 `right.get(0).length` 取列数,输入为空时抛 `IndexOutOfBoundsException`。这是**既有 bug,被去相关第一次暴露出来**(以前 join 两侧从不为空)。

> 教训:新功能让之前「从不出现的计划形态」第一次走到执行器,常会触发既有代码的隐藏缺陷。别急着在新代码里找错,先确认是不是老代码的 latent bug 被暴露了。

## 关键一课:同一算子可能有多种形态

这是本次最值得记的一课。实现 `IS NOT DISTINCT FROM` 时,我第一次写的是 `RexInterpreter` 里的 `IS_NOT_DISTINCT_FROM` 分支,让标量子查询通过了。但把 `WHERE x IS NOT DISTINCT FROM y` 直接写进 SQL 时,却报 `unsupported operator: IS TRUE`。

用探针打印真实计划,发现**同一句 `IS NOT DISTINCT FROM` 在两个地方出现,却是两种完全不同的 RexNode**:

- **标量子查询去相关**(`RelDecorrelator` 产出):相关键比较直接是 `IS NOT DISTINCT FROM($0, $2)` —— 一个操作符。
- **直接写在 WHERE**(`SqlToRelConverter` 解析期改写):被改写成 `IS TRUE(x = y)`(而 `IS DISTINCT FROM` → `IS NOT TRUE(x = y)`)—— 是**另一个**操作符。

```
WHERE x IS NOT DISTINCT FROM y
  → OR(AND(IS NULL(x), IS NULL(y)), IS TRUE(=(x, y)))      -- 不是 IS_NOT_DISTINCT_FROM

标量子查询相关键 join 条件
  → IS NOT DISTINCT FROM($0, $2)                            -- 是 IS_NOT_DISTINCT_FROM
```

如果我只信「标量子查询过了,说明 IS NOT DISTINCT FROM 实现了」,就会漏掉直接谓词这条路径。结论是**同一个 SQL 语义,在 Calcite 不同处理阶段会被改写/降级成不同的算子**,必须两个都覆盖。

> 教训:对「看起来同一个东西」保持怀疑。SQL 语义 → `SqlToRelConverter` 改写 → `RelDecorrelator` 产出,每一层都可能改头换面。用探针确认**每种形态实际长什么样**,而不是想当然地复用上一个实现。

## 复盘:这套方法可复用的地方

1. **先探针、后编码**:每个新功能先打印真实 RelNode,拿到「根因」再动手。
2. **根因 > 症状**:`EXISTS` 报 `unsupported operator` 是症状,根因是 `RexSubQuery` 未被处理;`IS TRUE` 报错是症状,根因是「同义算子有两种形态」。
3. **复用成熟组件**:去相关、子查询移除都交给 Calcite,不重造。
4. **测试驱动暴露 latent bug**:新功能让旧代码的新形态首次被执行,顺带修了空输入 join 崩溃等既有缺陷。
5. **把「同义不同形」当作常态**:同一 SQL 语义在解析、优化、去相关各阶段可能被改写成不同算子,逐一验证。
