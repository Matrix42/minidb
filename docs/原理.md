# Calcite 子查询与 EXISTS 支持原理

本文解释 MiniDB 为什么此前不支持 `EXISTS`,以及如何通过 Calcite 标准的「子查询移除 + 去相关」管线支持它。内容基于 2026-08-14 的代码状态。

## 现状(根因)

Calcite 的 `SqlToRelConverter` 默认配置 `expand=false`,把 `EXISTS` / `NOT EXISTS` / `IN (子查询)` / 标量子查询**保留为 `RexSubQuery`**,而不是展开成独立的 RelNode。

`RexSubQuery` 内嵌在 `LogicalFilter` / `LogicalProject` 的条件或投影表达式里,其 `rel` 字段持有一颗**逻辑子树**(`LogicalFilter`/`LogicalTableScan` 等)。相关子查询在这颗子树里通过 `LogicalCorrelVariable`(打印为 `$cor0.id`)引用外层列。

例如 `SELECT * FROM a WHERE EXISTS (SELECT 1 FROM b WHERE b.aid = a.id)` 经 `SqlToRelConverter` 直接产出:

```
LogicalProject(id=[$0], name=[$1])
  LogicalFilter(condition=[EXISTS({
LogicalFilter(condition=[=($1, $cor0.id)])
  LogicalTableScan(table=[[minidb, b]])
})], variablesSet=[[$cor0]])
    LogicalTableScan(table=[[minidb, a]])
```

关键点:**物理转换能通过,但 `RexInterpreter` 没有 `RexSubQuery` 的求值分支**。子查询以 `RexSubQuery` 身份一路流到 `MiniDbFilter`/`MiniDbProject`,执行时走 `RexInterpreter.evalCall` 的 default 分支 → `functions.lookup(...)` 返回 null → 抛 `unsupported operator`。这就是「EXISTS 不支持」的直接根因。

## 解决原理:子查询移除 + 去相关

Calcite 的标准做法(等价于 `Programs.standard()` 的前两步)是**在逻辑优化阶段、物理转换之前**,把 `RexSubQuery` 先提升再拆掉:

1. **`SubQueryRemoveRule`**(`FILTER`/`PROJECT`/`JOIN` 三个 config)——把 Filter/Project/Join 条件里的 `RexSubQuery` 提升为 `LogicalCorrelate` 节点(非相关子查询也可能直接改写为 join)。
2. **`RelDecorrelator.decorrelateQuery`**——把 `LogicalCorrelate` 去相关为普通 join/聚合/过滤,消除 `$cor0` 相关变量。

MiniDB 在 `LogicalOptimizer.optimize` 里、现有 HEP 逻辑规则之前,插入了这两步(`decorrelateSubqueries`)。去相关后的计划**只使用 MiniDB 已有的算子**,不新增任何物理算子,也不需要 SEMI/ANTI join。

### 去相关产物的实际形态

以 `a(id, name)` 与 `b(id, aid)` 两张表为例:

**非相关 `EXISTS (SELECT 1 FROM b WHERE b.id > 5)`** 变成(交叉连接 + 聚合压成单行):

```
LogicalProject(id, name)
  LogicalJoin(condition=[true], joinType=[inner])     -- 交叉连接
    LogicalTableScan(a)
    LogicalAggregate(group=[{0}])                     -- 按常量分组,压成 0 或 1 行
      LogicalProject(i=[true])
        LogicalFilter(b.id > 5)
          LogicalTableScan(b)
```

**非相关 `NOT EXISTS`** 变成(LEFT join + `IS NULL` 过滤):

```
LogicalFilter(condition=[IS NULL($2)])
  LogicalJoin(condition=[true], joinType=[left])
    LogicalTableScan(a)
    LogicalAggregate(group=[{0}]) ...                 -- 子查询非空时产出 1 行,空时 0 行
```

**相关 `EXISTS (SELECT 1 FROM b WHERE b.aid = a.id)`** 变成(等值 join + 按 aid 去重):

```
LogicalJoin(condition=[=($0, $2)], joinType=[inner])
  LogicalTableScan(a)
  LogicalProject(aid=[$0], $f1=[true])
    LogicalAggregate(group=[{0}])                     -- 按 aid 去重(去掉 b.aid 的 NULL)
      LogicalProject(aid=[$1])
        LogicalFilter(IS NOT NULL($1))
          LogicalTableScan(b)
```

**相关 `NOT EXISTS`** 是同一形态,只是 joinType 换成 `left`、外面包 `IS NULL`。这些计划里出现的 `INNER/LEFT join`、聚合、过滤、投影、`=`,MiniDB 全都已经支持。

## 附带改动(去相关暴露出的既有 bug)

去相关让一些之前从不出现的计划形态第一次走到执行器,暴露了三处既有缺陷:

1. **`IS NULL` / `IS NOT NULL` 谓词缺失**。去相关硬依赖它们(`NOT EXISTS` → `IS NULL`、相关 `EXISTS` → `IS NOT NULL`),而 `RexInterpreter` 之前没有这两个 `SqlKind` 分支。已在 `RexInterpreter` 新增 `nullTest` 专用 handler:非 STRICT(操作数为 null 时仍产出 true/false 而非 null),类型无关(任意向量)→ 产出 `BitVector`,逐行读 `isNull` 位。顺带让普通的 `WHERE col IS NULL` 也可用了。

2. **MiniDbJoin 空输入崩溃**。三个 join 子类(`MiniDbHashJoin`/`MiniDbSortMergeJoin`/`MiniDbNestedLoopJoin`)构造 null 填充行时用 `right.get(0).length`,当某侧输入为空(如 `EXISTS` 子查询空)时 `get(0)` 抛 `IndexOutOfBoundsException`。已改为用 `getLeft()/getRight().getRowType().getFieldCount()` 从行类型取列数(不依赖数据)。

3. **MiniDbJoinRule 把交叉连接误判为等值连接**。Calcite 的 `JoinInfo.isEqui()` 只看 `nonEquiConditions` 是否为空,`condition=true`(交叉连接)时两侧 key 都为空却仍返回 true,导致 `EXISTS` 的非相关交叉连接被路由到 `MiniDbSortMergeJoin`。已在 `MiniDbJoinRule` 增加 `joinInfo.leftKeys.isEmpty()` 守卫,空 key 的连接走 `MiniDbNestedLoopJoin`(任意条件路径)。

## 范围边界

- 本次支持:**EXISTS / NOT EXISTS**(相关 + 非相关)。
- 同管线附带:`IN (子查询)` 去相关后只用到 `=`/`>`/聚合,理论上可用,但未作专项测试。
- 明确不支持:**标量子查询**(`SELECT (SELECT ...)`)——去相关产物含 `IS NOT DISTINCT FROM` join 条件,`RexInterpreter` 尚未注册该算子。
